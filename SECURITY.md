# Security policy

Please report suspected vulnerabilities privately to the repository owner
instead of opening a public issue. Include the affected package and version, a
minimal reproduction when possible, and whether the issue crosses the gRPC,
SQLite, or provider boundary.

Use [GitHub's private vulnerability-reporting
form](https://github.com/KaiCode2/evm-fork-cache-hypersync/security/advisories/new).
Do not include credentials in the report or reproduction. Private vulnerability
reporting must be enabled before the repository is made public; if the form is
unavailable, publication is blocked until the repository owner enables it.

## Supported versions

| Version | Security support |
| --- | --- |
| `0.1.0-alpha.x` | Latest alpha supported until superseded |
| Versions older than `0.1.0-alpha.1` | Unsupported |

Security fixes are released on the latest alpha while the core integration is
pre-release. Stable `0.1.0` support begins only after the core dependency is
stable and this policy is updated.

## Dependency audit policy

CI runs cargo-audit 0.22.2 and cargo-deny 0.20.2 against the locked dependency
graph. Both tools are installed with an exact version and `--locked`.
`deny.toml` denies unreviewed registries, Git dependencies, wildcard
requirements, yanked releases, vulnerabilities outside the three exceptions
below, and licenses outside the reviewed allowlist. Unmaintained-crate warnings
remain visible and are reviewed during each release rather than failing the
gate. Before the audit, `scripts/check-security-exceptions.sh` asserts the exact
reverse dependency paths for every ignored advisory; the job fails if an
exception reaches a different workspace package or dependency.

The initial dependency graph has three explicit advisory exceptions:

- `RUSTSEC-2025-0055` covers `tracing-subscriber` 0.2.25. It is an inactive
  all-feature/all-target lockfile entry (`cargo tree --workspace --all-features
  -i tracing-subscriber@0.2.25 --target all` has no path to a workspace
  package). Because cargo-audit ignores this advisory by ID rather than by
  package instance, the scope script separately parses every locked and active
  `tracing-subscriber` version. It requires the exact vulnerable 0.2.25 entry
  to remain present and unreachable, rejects any other locked version below
  patched 0.3.20, and requires every active version to be 0.3.20 or newer. If
  0.2.25 disappears, the gate fails until the now-stale ignore is removed.
- `RUSTSEC-2025-0143` covers unsound safe constructors in `capnp` before 0.24.
  `hypersync-client` 1.4.0 and `hypersync-net-types` 0.12.3 currently require
  0.23, so Cargo cannot select the patched 0.24 release. The affected
  `StructSchema::new` calls in this graph are generated by Cap'n Proto from
  static schemas; the extension does not construct or accept schemas from
  provider data and does not call either affected API directly. This limits the
  practical exposure but does not erase the upstream memory-safety defect.
- `RUSTSEC-2026-0253` covers panic-unsafety in `lru` before 0.18.2. The pinned
  Alloy 1.6 line requires `lru 0.16` and is its only immediate consumer. Alloy's
  provider caches use `u64` block numbers and fixed `B256` hashes as keys; both
  have non-panicking destruction, while the advisory requires a panic during
  key destruction under unwinding before a later eviction. The scope script
  pins the exact `lru -> alloy-provider` edge. A new consumer, key type, or
  compatible Alloy release invalidates this exception.

The Cap'n Proto exception is restricted to the HyperSync adapter's transitive
dependency. It does not apply to the provider-neutral protocol, remote client,
event service, or `evm-fork-cache`. Before every release, check for an Envio
version using `capnp >= 0.24`; upgrade and remove the exception when available.
Do not add a broader Cap'n Proto use, dynamic or caller-supplied schemas, or a
direct `capnp` dependency while this exception exists. If those assumptions
change, the exception is invalid and publication must stop pending a fix or a
separate security review.

RustSec also reports unmaintained dependencies. These are not vulnerability
advisories, but the release scope check makes their acceptance explicit:

- Hybrid coordinator checkpoint V5 uses a private canonical `alloy-rlp` schema
  and has no direct `bincode` dependency. Unmaintained `bincode` 1.3.3 remains
  reachable only through `evm-fork-cache`'s compatibility-bound, already
  versioned cache formats and `hypersync-client` 1.4.0. No extension crate may
  add either bincode generation. Core owns its format-migration decision;
  Envio owns the other upstream path.
- `derivative` 2.2.0 is an unreachable lockfile entry and is accepted only
  while it remains unreachable.
- `paste` 1.0.15 is an active transitive procedural macro through the pinned
  Alloy/Arkworks/Parquet graph. It is not called by workspace code at runtime;
  its immediate reverse-dependency set is pinned until upstreams migrate.

Any changed path fails `scripts/check-security-exceptions.sh` and requires a
fresh review. Remove stale entries and exceptions as soon as the upstream
constraints disappear.

## CI action pinning

Every third-party action is pinned to an immutable full commit SHA. The adjacent
comments retain the reviewed human-readable upstream ref:

| Action | Reviewed ref | Pinned commit |
| --- | --- | --- |
| [`actions/checkout`](https://github.com/actions/checkout/releases/tag/v4.4.0) | `v4.4.0` | `11d5960a326750d5838078e36cf38b85af677262` |
| [`dtolnay/rust-toolchain`](https://github.com/dtolnay/rust-toolchain/commit/4cda84d5c5c54efe2404f9d843567869ab1699d4) | `stable` | `4cda84d5c5c54efe2404f9d843567869ab1699d4` |
| [`Swatinem/rust-cache`](https://github.com/Swatinem/rust-cache/releases/tag/v2.9.1) | `v2.9.1` | `c19371144df3bb44fab255c43d04cbc2ab54d1c4` |

The Rust toolchain action uses the same reviewed action commit for stable and
MSRV jobs; the requested toolchain is an explicit input. Updating any action
requires verifying the new upstream ref and commit before changing the pin.

## Secret scanning

CI runs Gitleaks 8.30.1 in both directory mode and full-history Git mode with
redacted output. `.gitleaks.toml` extends the scanner's default rules and
excludes the intended local `.env`, Git internals, and generated `target`
output; `.env.example` remains scanned. `scripts/check-secrets.sh` rejects any
other scanner version so local and CI results use the same rules engine. Its
separate historical `.env` guard consumes NUL-delimited paths and emits only a
count if one was ever committed.

Before release, a maintainer with the local credential-bearing `.env` must also
run `scripts/check-exact-secret-leaks.sh`. That separate gate searches the
worktree and every reachable commit for the exact `ENVIO_API_TOKEN` and
`RPC_URL` values while reporting only aggregate counts. Filenames remain
NUL-delimited internally, and the gate never prints paths, secrets, or matching
lines—even if a filename contains a secret, newline, or control character. It
excludes the current `.env` itself. CI runs
`scripts/test-publication-security-gates.sh` with synthetic values to verify
these failure-output guarantees; the real exact-value gate remains local-only.
Do not upload its output, pattern file, or `.env` to CI.
